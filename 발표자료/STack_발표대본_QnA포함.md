## 2. 문제 정의

### ① 이클래스 자체의 불편함

[영상: S03 문제 상황 23초(인트로 3초 포함), 내레이션+자막] *(콘티는 부록 A-1 · 영상이 끝날 때까지 말하지 않고 화면에 집중 유도)*

[슬라이드: S04 숫자 두 개 - 클릭 8회 / 화면·앱 전환 4회]

방금 보신 것처럼 과목에 들어가서 자료 하나를 내려받고, 다운로드 폴더와 PDF 뷰어, 외부 AI 앱을 거쳐 다시 이클래스로 돌아와 과제 마감까지 확인하는 데 클릭 여덟 번, 화면과 앱을 네 번이나 옮겨 다녀야 합니다. 한 과목만 해도 이렇습니다. 마감일, 강의자료, 녹음, 그 녹음을 다시 들으며 하는 필기까지 전부 따로 놀고 있기 때문입니다. *(말하기 약 0:29 / 공백 제외 143자)*

### ② 기존 대안의 한계

[슬라이드: S05 기존 대안의 두 가지 한계 - ① 업로드형: 흐름이 끊김 ② 연동형: 계정을 맡김 (충북대 11/10·서경대 11/9 외부 서비스 계정 입력 금지, 유비온 11/3 IP 차단 지원)]

방금 영상에서도 보셨듯이, AI로 복습하려고 PDF를 내려받아 외부 서비스에 일일이 다시 올리죠. 그런데 기존 대안들은 결국 둘 중 하나를 포기하게 만듭니다. 먼저, 유니브 AI 같은 업로드형은 파일이 앱마다 흩어지다 보니 나중에 볼 때 '이 PDF가 몇 주차 과제랑 이어지는 거지?' 하고 매번 다시 맞춰봐야 합니다. 과목이나 마감 일정은 모르니까요. 반대로 GPAI 같은 연동형은 학교 아이디와 비밀번호를 외부 서버에 맡겨 두고, 그 서버가 대신 로그인해서 자료를 가져오는 방식인데요. 실제로 이번 달에 충북대와 서경대가 외부 서비스에 학교 계정을 입력하지 말라고 공지했고, 이클래스 운영사 유비온도 IP 차단을 안내했습니다. 잘 쓰던 도구가 하루아침에 막히는 셈입니다. 결국 업로드형 AI는 학습 흐름이 끊기고, 연동형 AI는 계정을 맡겨야 해서 학교가 막고 있습니다. 저희는 바로 그 사이를 풀고 싶었습니다. *(말하기 약 1:09 / 공백 제외 346자)*

## 3. 해결 방식

[슬라이드: S06 문제 → 원칙 매핑 도식 (원칙 1 한 화면 흐름 / 원칙 2 과목 안에 묶기 / 원칙 3 자동 정리·녹음하면 필기는 자동으로)]

저희는 이 두 가지 문제를 각각 원칙 하나로 풀었습니다. 첫째, '한 화면 흐름'입니다. 예전처럼 복잡한 하위 메뉴를 뒤질 필요 없이, 에이전트한테 말만 걸면 원하는 강의나 과제, 자료 페이지를 바로 찾아 열어 줍니다. 마감 확인부터 자료 보기, 요약, 강의 녹음까지 한 화면에서 쭉 이어집니다. 둘째, '과목 안에 묶기'입니다. 자료를 외부 앱으로 빼돌리지 않고 해당 과목과 주차 방 안에만 차곡차곡 모아둬서, 학교 서버가 불안정할 때도 내 복습은 멈추지 않습니다. 학교 계정은 로그인할 때 한 번만 확인하고 비밀번호는 저장하지 않습니다. 마지막 셋째는 '자동 정리'입니다. PDF를 올리면 페이지마다 해설이 붙은 요약으로 정리됩니다. 그리고 수업은 녹음만 하면 필기는 STack이 대신합니다. 녹음하는 동안 바로 받아 적고, 끝나면 시각별 전사와 요약으로 같은 과목 학습실에 쌓입니다. *(말하기 약 1:07 / 공백 제외 334자)*

## 4. 시연

[슬라이드: S07 핵심 기능 4단계 - ① 홈 마감 확인(드릴다운도 그대로) → ② 에이전트로 바로 이동(명령창에 과목명을 쓰면 강의실로) → ③ 요약 화면(요약·질의응답) → ④ 강의 녹음·자동 필기]

말보다 화면으로 직접 보시는 게 빠를 텐데요. STack을 처음 켜는 학생 입장에서, 에이전트로 원하는 기능을 바로 불러내 강의 녹음으로 필기까지 끝내는 과정을 1분 47초 동안 보여드리겠습니다. 할 일이 많을 땐 플랜 모드에 한 번에 맡기는 모습도 함께 보시겠습니다. *(말하기 약 0:23 / 공백 제외 113자)*

[영상: S08 시연 영상 1분 47초(1:47), 내레이션+자막] *(장면 구성 및 타임코드는 부록 A-2 · 영상이 재생되는 동안에는 말하지 않고 다음 코드 파트 호흡 정리)*

방금 보신 것처럼 클릭 여덟 번, 화면 전환 네 번을 오가던 복습이, 이제는 말 한마디로 원하는 강의실을 열고 과목 학습실 안에서 끝까지 이어집니다. 할 일이 여러 개면 플랜 모드가 순서대로 이어 줍니다. *(말하기 약 0:17 / 공백 제외 83자)*

## 5. 코드·설계

[슬라이드: S09 원칙 1·2·3 ↔ 코드 구조도]

말로만 원칙을 세운 건 아니고, 실제 코드 구조도 이 세 가지에 맞춰 설계했습니다. 먼저 첫 번째, 한 화면 흐름과 에이전트 기능은 프론트엔드의 에이전트 실행 모듈과 백엔드 API 서버에 구현했습니다. 과목 학습실에 한 번 들어가면 마감, 자료, 요약, 녹음이 전부 같은 상태를 공유하도록 짰고요. 두 번째, 과목 안에 묶기는 파일 저장 모듈과 서버의 학습실 서비스가 담당합니다. 올린 파일은 수강 과목에, 녹음은 사용자와 과목에 딱 묶어둬서 다른 과목이나 다른 사람이 볼 수 없고, 학교 서버가 흔들려도 학습 데이터는 STack 서버에 안전하게 남습니다. 세 번째, 자동 정리는 PDF의 경우 서버의 요약 파이프라인에서, 수업 녹음은 올리자마자 서버가 전사와 요약을 만들어 녹음 학습 화면에 필기처럼 보여 줍니다. 처음엔 저희도 기능별로 페이지를 따로 나눌까 고민했습니다. 하지만 페이지가 갈라지면 결국 기존 이클래스와 다를 게 없어진다고 판단해서, 에이전트와 한 화면 구조를 묶는 쪽을 택했습니다. *(말하기 약 1:16 / 공백 제외 379자)*

[슬라이드: S10 에이전트 동작 - 말 한마디 → 7가지 동작 중 하나 → 서버가 다시 검증 → 정해진 화면으로만]

말 한마디에 수강 과목과 할 일 목록을 붙여 보내면, AI는 이동, 고르기, 계획처럼 정해 둔 일곱 가지 동작 중 하나만 고릅니다. 서버가 그 답이 내 과목, 내 할 일인지 다시 검증하고, 정해진 화면 경로로만 이동시킵니다. *(말하기 약 0:18 / 공백 제외 91자)*

## 6. 사업 모델·시장

[슬라이드: S11 시장 규모·확장 전략 - 부제 "기존 LMS엔 붙이고, 이클래스와는 묶어 학교와 계약합니다." · 왼쪽 TAM 908.8억·SAM 711.1억·SOM 48.1억, 오른쪽 두 트랙(A 애드온 연 3만 원·B 묶음 연 5만 원) × 3단계 목표 연 매출 3.3억 → 27.3억 → 48.1억]

확장은 두 가지 트랙으로 갑니다. 트랙 A는 학교가 이미 쓰고 있는 이클래스나 LMS에 STack만 얹는 애드온 방식이고, 트랙 B는 저희가 개발 중인 이클래스와 STack을 묶어 LMS 전체를 교체하는 방식입니다. 둘 다 학교와 연간 계약하는 B2B 모델이고, 가격은 학생 한 명당 연 3만 원, 5만 원으로 책정했습니다. 서울대가 생성형 AI 서비스에 1인당 연 8만 원 넘게 책정한 것과 비교하면 부담을 낮춘 수준입니다. 트랙 B 기준으로 보면 전국 4년제와 전문대 재학생 181만 명, 약 909억 원이 전체 시장이고, 4년제만 따져도 약 711억 원 규모입니다. 첫해에는 서울과기대에 애드온으로 도입해 약 3억 3천만 원, 둘째 해에는 국립대로 넓혀 약 27억 원, 셋째 해에는 사립대까지 총 열다섯 개 대학, 약 48억 원 매출이 목표입니다. 애드온으로 먼저 진입하고, LMS 교체 시기가 온 학교는 묶음으로 가져가겠습니다. *(말하기 약 1:10 / 공백 제외 349자)*

- **정의**

  - SAM: 4년제 재학생 1,422,139명(국공립 29개교 316,126명 + 사립 159개교 1,106,013명) × 연 5만 원 = 711.1억 원. A 가격만이면 426.6억 원.

## 부록 B. 예상 질문 7개와 답 (코드 근거)

**Q1. 에이전트는 말을 어떻게 페이지 이동으로 바꾸나요?**
> "입력창(`command-bar.tsx`)에 문장을 치면 `run.ts`의 `ask()`가 `POST /api/assistant`로 학생 문장과 수강 과목·할 일 목록을 보냅니다. 그러면 `server.mjs`의 `assistant()`가 Gemini를 호출하는데, `responseSchema`를 걸어서 답을 정해 둔 행동 유형(`go`, `choose`, `plan`, `revise`, `reject`, `none`, `clarify`)과 과목·활동 ID 목록 안에서만 고르게 제한했습니다. 모델이 고른 답은 서버가 한 번 더 검증하고, 프론트엔드의 `execute()`가 `hrefFor`와 `routeFor`로 미리 정의해 둔 경로로만 화면을 이동시킵니다. 프롬프트 인젝션을 막기 위해 과목명이나 할 일 제목 안의 지시는 따르지 말라고 시스템 프롬프트에 명시했고, IP당 분당 10회 호출과 7초 타임아웃 제한도 걸어 뒀습니다."

**Q2. 녹음은 어떻게 필기로 바뀌나요?**
> "필기는 두 단계로 만들어집니다. 먼저 녹음하는 동안에는 브라우저 음성 인식(Web Speech API, 한국어)으로 화면 아래에 실시간으로 받아 적습니다(`live-transcript.ts`). 이건 화면에만 보이고 저장하지 않습니다. 녹음은 브라우저의 `MediaRecorder`로 받아(`course-recordings.ts`) 서버에 올리는데, 올리는 순간 서버가 전사와 요약 작업을 자동으로 대기열에 넣습니다(ADR-0041). 보안 검사를 통과한 녹음만 Deepgram `nova-3` 모델로 전사하고, `language=multi`에 한국어·영어 힌트를 줘서 한 강의 안에 섞인 한국어와 영어를 한 번에 받아 적습니다. 말이 멈추는 발화 단위마다 시작 시각이 붙어서, 녹음 화면(`recording-study.tsx`)에서 전사 줄을 누르면 그 시각부터 바로 재생됩니다. 요약은 PDF 요약에 쓰는 기존 요약 모델로 만들고, 형식이 틀리거나 녹음 길이 밖의 시각이 나온 출력은 서버가 버리고 다시 만듭니다. 결과는 녹음 주인 한 명만 볼 수 있고, 녹음을 지우면 전사와 요약도 같이 지워집니다."
> *(근거: STack-Backend main `docs/adr/0041-recording-transcription-and-summary.md`·`integration/deepgram/DeepgramSpeechToText.java`, Frontend-final main `src/shared/live-transcript.ts`. 시각은 단어 단위가 아니라 발화 단위. 녹음 하나 180분, 하루 300분 한도)*

**Q3. 데이터는 어디에 저장되고 누가 볼 수 있나요?**
> "강의자료와 요약 결과는 STack 서버 저장소에 두고, 파일 접근은 `files.api.FileAccess`가 해당 과목 수강 권한을 판정합니다. 녹음과 학습실 폴더는 `/api/me/study-room/**` 경로 아래에서 소유자 본인만 접근할 수 있고, 다른 사람 ID로 조회하면 존재하지 않는 것처럼 404를 반환합니다. DB 레벨에서도 `(owner_user_id, ID)` 복합 외래키로 남의 폴더에 데이터를 넣지 못하게 막았고, 교수나 운영자가 학생 개인 녹음을 열람하는 경로는 아예 없습니다(ADR-0040 3번)."

**Q4. DeepSeek이면 중국 서버로 가는 것 아닌가요? 모델은 바꿀 수 있나요?**
> "PDF 요약의 기본값은 DeepSeek API이고 처리 지역은 중국이 맞습니다. 다만 제공자는 언제든 바꿀 수 있게 설계했습니다. OpenAI 호환 API라면 `ASTRA_LLM_BASE_URL`과 `ASTRA_LLM_MODEL` 환경변수만 바꾸면 되고, README에 Gemini 설정 예시도 넣어 뒀습니다(`LlmProperties.java`). 강의자료는 교수자가 동의하기 전에는 외부로 나가지 않고, 동의 화면에서 제공자·처리 지역·학습 이용 여부·국외 이전을 명시적으로 보여 줍니다. 제공자를 바꾸면 다시 동의를 받도록 했습니다(ADR-0032). 또 모델로 넘어가는 텍스트는 `PatternRedactor`가 이메일, 휴대전화 번호, 학번 형식 숫자를 마스킹합니다. 물론 이름이나 페이지 이미지 속 글자까지는 못 가리는 한계가 있고요. 수업 녹음은 올린 학생 본인 것만 전사(Deepgram, 기본 미국 처리·EU로 바꿀 수 있음)와 요약 모델로 보내고, 사용자 이름이나 과목명은 같이 보내지 않습니다. Deepgram 모델 개선 프로그램에서도 빼서 처리하는 동안만 보관하게 했습니다(ADR-0041). 홈 에이전트는 별도로 Gemini를 쓰는데, 이때 보내는 건 과목명과 할 일 제목·마감·진행률 같은 목록 메타데이터뿐입니다(`run.ts` 요청 본문)."

**Q5. STack도 학번이랑 비밀번호를 받는데, GPAI랑 뭐가 다른가요?**
> "처음 로그인할 때 학번과 비밀번호를 받는 건 맞습니다. 학교 e-Class에 본인 확인을 하기 위해서입니다(`POST /api/auth/eclass-login`). 하지만 GPAI 같은 연동형과 세 가지가 다릅니다. 첫째, 비밀번호는 그 확인 요청 한 번에만 쓰고 DB 어디에도 저장하지 않습니다. 그래서 저희 서버가 학생 계정으로 혼자 학교에 다시 로그인할 수 없습니다. 둘째, 로그인으로 열린 학교 세션은 서버 메모리에만, 그 학생이 STack에 로그인해 있는 동안만 두고, 로그아웃하거나 세션이 끝나면 바로 버립니다. DB와 로그에는 남기지 않습니다(ADR-0043). 이 세션으로 하는 일도 정해져 있습니다. 로그인할 때 강의실의 주차·활동 목록을 한 번 읽어 오고(ADR-0042), 그 뒤로는 학생이 STack에서 자료나 공지를 직접 열 때만 그 항목을 읽습니다. 뒤에서 몰래 긁어 오거나, 과제를 대신 내거나, 영상 출석·2차 인증을 건너뛰는 요청은 아예 보내지 않습니다. 셋째, 학교가 거절한 로그인은 학번당 15분에 10번, 접속 주소당 30번까지만 받고, 넘으면 학교에 묻지 않고 바로 막습니다. 학교 계정 잠금이나 비밀번호 대입 공격에 저희가 악용되지 않게 하려는 장치입니다(`SchoolPasswordController`). 정식 서비스 단계에서는 학교 통합 로그인인 OIDC(ADR-0017)로 바꾸는 걸 전제로 설계했습니다."
> *[확인 필요: 학교 승인 여부, 시연에서 어떤 로그인을 쓰는지]*

**Q6. 다른 학교에도 쓸 수 있나요?**
> "학교 인증 로직이 `SchoolPasswordVerifier` 인터페이스로 분리돼 있습니다. 지금 붙어 있는 건 서울과기대 e-Class(ILOS)용 `EclassPasswordVerifier` 하나이고, 다른 학교는 그 학교용 구현체 하나만 추가하면 됩니다. 학교에 IdP가 구축돼 있다면 OIDC 로그인(ADR-0017)으로 바로 붙일 수도 있고, 요약·녹음·학습실 핵심 기능은 학교와 무관하게 STack 내부에서 독립적으로 동작합니다."

**Q7. 학교 서버가 죽으면 STack도 안 되나요?**
> "이미 올려 둔 자료와 요약, 녹음, 한 번 열어서 STack에 받아 둔 학교 파일은 전부 STack 서버에 있어서 학교 서버가 다운돼도 그대로 열립니다. 강의실 주차·활동 목록도 로그인 때 읽어 둔 사본으로 보입니다(ADR-0042). 이미 발급받은 로그인 세션도 STack 자체 세션이라 계속 유지됩니다. 다만 학교 계정으로 새로 로그인할 때와, 아직 열어 보지 않은 학교 자료 본문·파일을 처음 열 때는 학교 서버를 거쳐야 해서 그때는 열리지 않습니다(ADR-0043). 수강과목 동기화가 실패해도 로그인은 성공시키고 로그만 남기며, 학교 인증 자체가 실패할 때만 로그인이 안 됩니다(`SchoolCourseSync`)."
