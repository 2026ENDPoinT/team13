# ADR-0028 개인 파일함은 사용자별 사용량 행으로 차례를 정하고, 다시 쓰기는 같은 내용을 참조하는 새 파일로, ZIP은 worker가 저장소에서 저장소로 흘려 만든다

## 상태
채택 (2026-11-11)

## 맥락
개인 파일함(화면 12, EP-0244~0264)은 로그인한 사용자가 자기 파일을 폴더로 정리하고, 휴지통에 넣었다 되돌리거나 영구 삭제하고, 과제·자료 첨부로 다시 쓰고, 여러 개를 ZIP으로 받는 기능이다. 원본 client는 하위 항목 목록을 DOM에서 모아 보내고(FILES-07), 남의 seq를 섞을 수 있는 일괄 명령을 받으며(SEC-08), 페이지 크기·정렬·ZIP 한도를 서버가 강제하는지 알 수 없다(SEC-18, FILES-08). 파일함 삭제가 제출물 열람을 깨뜨릴 수 있다는 경고 문구도 있다(FILES-06).

V1에 `filebox_items`(부모 자기참조, active/trashed/purged, 같은 폴더 안 활성 이름 유일), `zip_jobs`, `zip_job_items`가 있고, 파일은 `files`와 내용 단위 `file_blobs`(참조 수, ADR-0011의 GC)로 저장한다. 업로드는 정책·이름·내용 형식·악성코드 검사를 거친다(ADR-0010, ADR-0018).

## 결정
1. 항목은 소유자 한 사람의 것이다. 사용자는 session principal에서만 정한다. 항목 ID, 부모 폴더 ID, 이동 대상 폴더 ID 가운데 하나라도 요청한 사람의 것이 아니면 요청 전체를 404로 거부하고 아무것도 바꾸지 않는다.
2. 한 사용자의 트리 변경(폴더 만들기, 이름 바꾸기, 이동, 휴지통, 복원, 영구 삭제, 올리기, ZIP 요청)은 새 테이블 `filebox_quotas`의 그 사용자 행을 먼저 `FOR UPDATE`로 잠근 뒤 처리한다. 순환 이동, 깊이, 항목 수, 용량 검사가 다른 명령과 엇갈리지 않는다. 잠금 순서는 `filebox_quotas → filebox_items → file_blobs → files → upload_sessions`이고, 명령은 READ COMMITTED transaction에서 하며 교착이나 잠금 대기 초과면 통째로 다시 한다(3번까지).
   - 항목 행마다 잠그는 방식은 기각했다. 순환 검사는 대상의 조상 전체를, 휴지통은 하위 전체를 보므로 잠글 행이 많고 순서를 정하기 어렵다. 한 사람이 동시에 보내는 명령은 드물어 사용자 단위 직렬화의 비용이 작다.
   - `users` 행을 잠그는 방식은 기각했다. 다른 모듈의 테이블이다.
3. 용량: 사용자 한 사람의 한도는 `filebox_quotas.quota_bytes`가 있으면 그 값, 없으면 `astra.filebox.quota`(기본 1 GB)다. 휴지통 파일도 영구 삭제할 때까지 센다. 항목 수(기본 5000)와 폴더 깊이(기본 10)도 같은 행을 잠근 뒤 센다. 올리기는 업로드 기록과 같은 transaction에서 내용 객체를 잠그기 전에 용량을 잡고(`UploadService.Placement`), 저장하기 전에 잠그지 않고 한 번 더 본다. 동시에 올려도 한도를 넘지 않는다.
4. 이름은 업로드 이름과 같이 정규화한다(`FileNames`). 입력한 이름에는 경로 구분자와 제어 문자를 받지 않는다. 같은 폴더 안 활성 항목의 이름 유일성은 DB 제약(대소문자 구분 없는 collation)이 지킨다. 사용자가 입력한 이름이 겹치면 409이고, 올리기와 복원은 " (1)" 같은 접미사를 붙인다. 파일 이름을 바꿀 때 확장자는 바꾸지 못한다.
5. 휴지통: 고른 항목과 그 아래 활성 항목 전체(서버가 계산한 폐포)를 한 묶음으로 넣고 `filebox_items.trash_root_id`에 고른 항목을 기록한다. 고른 항목 안의 항목을 함께 골라도 위 항목의 묶음이 된다. 복원과 영구 삭제는 휴지통 root만 받는다. 복원은 같은 묶음만 되돌리고, 원래 폴더가 활성이고 깊이 상한 안이면 그 폴더로, 아니면 루트로 되돌린다(backend/60 3.2절). 위쪽 root부터 되돌린다. 영구 삭제는 root 아래 휴지통 항목 전체를 `purged`로 바꾸고, 파일마다 `FileReferences.release`로 참조를 한 번 놓는다. 상태를 조건으로 건 UPDATE라 두 번 불러도 한 번만 줄고, 마지막 참조였던 내용 객체는 저장소 GC(ADR-0011)가 지운다. 항목 행은 tombstone으로 남긴다(ZIP 작업, 다시 쓴 파일의 출처가 가리킨다).
6. 올리기: 용도 `filebox`(`upload_policies`, 과목 없음)로 일반 업로드와 같은 검사를 거친다. 업로드는 기록과 함께 `attached`가 되므로 `Attachments`로는 첨부하지 못한다. 검사기가 있으면 검사를 마칠 때까지 `scanning`이고 내려받기, ZIP, 다시 쓰기를 하지 못한다.
7. 다시 쓰기(`POST /api/uploads:fromFilebox`, EP-0126): 같은 내용 객체를 참조하는 새 `files` 행(참조 수 +1, `files.source_filebox_item_id`)과 `clean` 업로드를 만든다. 대상 용도의 과목 역할, 확장자, 크기 정책을 다시 보고, 검사를 마치지 않았거나 거부한 내용은 409다. 만든 업로드는 일반 업로드처럼 부모 저장에서 `Attachments.attach`/`change`로 첨부한다. 첨부는 파일함과 따로 참조하므로 파일함에서 영구 삭제해도 제출물과 자료의 파일은 남는다(FILES-06, N-08).
   - 파일함의 `files` 행을 첨부가 함께 가리키는 방식은 기각했다. 영구 삭제가 첨부된 파일을 지우거나, `files`에 참조 수를 하나 더 두어야 한다. 업로드 하나는 부모 하나에만 첨부한다는 규칙(backend/60 3.1절)과도 맞지 않는다.
   - 내용을 복사하는 방식은 기각했다. 같은 내용은 객체 하나라는 규칙(ADR-0010 5번)이 있고 저장 비용이 는다.
8. 연결된 곳(EP-0256): 다시 쓴 파일 가운데 첨부된 것을 `source_filebox_item_id`로 찾고, 요청한 사람이 지금 그 부모를 볼 수 있는지 `FileAccess`(부모 모듈의 판정)로 거른다. 계산하므로 `filebox_items.reference_count` 캐시 column은 지웠다.
9. 목록: 폴더 하나의 활성 항목을 폴더 먼저, 정렬 key allowlist(`name`, `size`, `date`)와 방향(`asc`, `desc`) 순서로 keyset cursor 쪽으로 나눈다(쪽당 1~100). cursor에 정렬 방식을 담아 다른 정렬의 cursor는 400이다. 검색어는 그 폴더 바로 아래 항목의 이름에서 찾고 `%`, `_`는 글자 그대로 찾는다. 휴지통은 `GET /api/filebox/trash`로 따로 둔다.
10. 이름 바꾸기는 ADR-0011처럼 `If-Match`로 version을 받는다. 일괄 이동은 header 하나에 version을 여러 개 담지 못하므로 본문에 항목마다 version을 받는다(backend/60 7절).
11. ZIP(EP-0262~0264): `POST /api/filebox/zip-jobs`는 `Idempotency-Key`가 필요하고 검사와 기록만 한 뒤 202로 끝난다. 항목은 요청한 사람의 활성 파일이고 검사를 통과했어야 한다(폴더는 받지 않는다). 항목 수(100), 크기 합(500 MB), 사용자당 기다리거나 만드는 중인 작업 수(2)에 상한이 있고, 같은 항목 집합의 진행 중이거나 내려받을 수 있는 작업이 있으면 그 작업을 돌려준다.
   - worker는 작업을 `FOR UPDATE SKIP LOCKED`와 lease로 하나씩 잡고, 파일을 하나 넣을 때마다 lease를 늘린다. 원본을 content bucket에서 읽어 바로 압축해 `zips/{작업 ID}/{임의 값}.zip`에 multipart upload로 쓴다. 메모리에는 part 하나(8 MiB)만 두고 로컬 디스크에 쓰지 않는다. 완료는 lease 소유자를 조건으로 한 compare-and-set이고, lease를 잃은 worker는 쓴 객체를 지운다.
   - 항목 이름의 `/`, `\`는 `_`로 바꾼 뒤 업로드 이름처럼 정규화하므로 절대 경로와 `..` 경로 조각이 생기지 않는다. 대소문자만 다른 이름도 겹친 것으로 보고 접미사를 붙인다. 이름은 UTF-8이고 UTF-8 flag를 켠다.
   - 생성물은 요청한 사람만 TTL(2시간) 동안 내려받는다. 지나면 410이고 worker가 `zips/{작업 ID}/`를 지운다. 항목이 휴지통에 갔거나 내용이 사라졌으면 `failed`(`item_unavailable`), 저장소 오류는 3번까지 다시 한 뒤 `failed`(`build_failed`)다.
   - 생성물을 `files` 행으로 두는 방식(V1의 `zip_jobs.result_file_id`)은 기각했다. 내용 중복 제거, 검사, 첨부 GC의 대상이 아닌 임시 객체다. column을 지우고 `result_storage_key`를 직접 둔다.
12. 모든 변경 명령과 내려받기는 감사 기록을 남긴다. 파일함 변경 명령(`filebox-write`), ZIP 요청(`filebox-zip`), 올리기와 다시 쓰기(`upload`)에 사용자 단위 요청 제한이 있다.

## 결과와 트레이드오프
- 한 사용자의 명령은 서로 기다린다. 다른 사용자의 명령과는 기다리지 않는다.
- 휴지통 보존 기간(EP-0260 미확인)을 정하지 않아 자동 영구 삭제가 없다. 휴지통 파일은 용량을 계속 차지한다.
- 원본 화면처럼 과제 제출 같은 활동 업로드를 파일함에 자동으로 넣지 않는다(backend/60 3.2절 INFERRED). 넣으려면 제출 확정과 같은 transaction에서 파일함 항목을 만드는 API가 필요하다.
- 올리기 기록이 용량 초과처럼 저장 뒤에 실패하면, 처음 보는 내용을 기본 key에 저장한 객체는 남는다(같은 내용의 다른 요청과 함께 쓸 수 있어 지우지 않는 기존 업로드 규칙). 저장 전에 용량을 한 번 보므로 드물다.
- worker가 multipart upload 도중에 죽으면 끝내지 못한 part가 남는다. content bucket의 lifecycle 규칙(`abort_incomplete_multipart_days`)이 지운다.
- ZIP에는 폴더를 넣지 못한다. 넣으려면 폴더 구조를 경로로 만드는 규칙(정규화한 이름 조각만 쓰기)을 더한다.
- 요청 제한 counter는 process 메모리에 있다(architecture.md 8절).
